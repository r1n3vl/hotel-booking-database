# Как разобраться в проекте и объяснить его на собеседовании

## Что это за проект

Hotel Booking Database — операционная база данных небольшой сети отелей на Microsoft SQL Server. Она хранит отели, номера, гостей и бронирования, проверяет доступность номеров, учитывает дополнительные услуги и платежи, строит отчёты.

Основная логика написана на T-SQL. Python нужен для создания базы и автоматических тестов. Docker нужен для удобного запуска SQL Server. Веб-интерфейса в проекте нет.

Это отдельный проект по SQL и проектированию OLTP-базы. Он дополняет проект Spotify Data Warehouse: здесь основной вопрос — как правильно записывать и изменять данные, а в хранилище — как подготавливать их для аналитики.

## В каком порядке изучать

1. Запусти базу по README и посмотри таблицы в SSMS.
2. Открой `docs/data-dictionary.md` и найди связи Hotel → Room → Booking, Guest → Booking.
3. Выполни SELECT по одной брони, затем найди её услуги, платежи и историю статусов.
4. Пройди `examples/01_booking_lifecycle.sql` по шагам.
5. Разбери `api.usp_CreateBooking`: параметры, проверки, блокировка, INSERT, COMMIT, обработка ошибки.
6. Разбери `report.vBookingFinancials`: почему услуги и платежи сначала агрегируются отдельно.
7. Изучи отчёты и запусти тесты. Особое внимание — тестам двух одновременных запросов.

## Объяснение за 40–60 секунд на английском

> This is a hotel booking database built with Microsoft SQL Server. It manages hotels, rooms, guests, reservations, services and payments. I separated the storage tables, business procedures and reporting views into different schemas. The main challenge is preventing double bookings when two requests arrive at the same time. The booking procedure takes a transaction-level lock for the room, checks availability and inserts the reservation in one transaction. The project also includes payment idempotency, status history, occupancy reports and integration tests against SQL Server.

Используй этот текст после того, как разберёшь соответствующий код. На уточняющий вопрос лучше объяснить конкретный пример из проекта, чем перечислять термины.

## Как связаны таблицы

Один отель содержит много номеров. Каждый номер принадлежит одному типу: single, double, triple или family. Тип определяет вместимость; сам номер хранит текущую цену.

Гость может иметь много бронирований. Каждое бронирование относится к одному номеру. В бронировании сохраняются даты, число взрослых и детей, статус и согласованная цена за ночь.

У одного бронирования может быть несколько услуг и несколько платежей. Например, проживание — 600 PLN, завтрак — 50 PLN, парковка — 120 PLN. Гость может сначала внести 200 PLN, а позднее ещё 570 PLN. Общая стоимость — 770 PLN, оплачено — 770 PLN, остаток — 0.

`BookingService` хранит каждое начисление отдельно. `Payment` хранит каждое движение денег отдельно. Отмена платежа здесь представлена новой записью REFUND, а не удалением старого CAPTURE.

## PK и FK

Primary key однозначно определяет строку. Например, `BookingID` определяет бронирование.

Foreign key связывает строку с другой таблицей. `Booking.RoomID` ссылается на `Room.RoomID`, поэтому нельзя создать бронирование для несуществующего номера.

У номера есть также бизнес-ограничение: пара `(HotelID, RoomNumber)` уникальна. Номер 101 может существовать в разных отелях, но не дважды в одном отеле.

## Что здесь означает нормализация

Название отеля не копируется в каждое бронирование. Бронирование ссылается на номер, а номер — на отель. Изменение адреса отеля не требует обновлять сотни бронирований.

Цена в бронировании всё-таки копируется специально: это согласованная историческая цена. Если завтра стоимость номера изменится с 200 на 250 PLN, старое бронирование должно остаться по 200 PLN.

На английском:

> I normalized the operational entities, but I store agreed prices as snapshots because historical bookings must not change when catalog prices change.

## Когда даты пересекаются

Бронь с 10 по 13 мая занимает ночи 10, 11 и 12 мая. Новая бронь с 13 мая допустима: предыдущий гость уже выезжает.

Условие пересечения:

```sql
existing.CheckInDate < requested.CheckOutDate
AND existing.CheckOutDate > requested.CheckInDate
```

Здесь используются строгие `<` и `>`. Если заменить их на `<=` и `>=`, выезд и заезд в один день ошибочно будут конфликтовать.

## Почему одной проверки SELECT недостаточно

Представь два запроса на один номер:

- Первый проверил доступность: свободен.
- Второй тоже проверил доступность: свободен.
- Оба создали бронирования.

Транзакция сама по себе не гарантирует защиту от такой гонки при обычном READ COMMITTED. В проекте используется `sp_getapplock` для ресурса конкретного номера. Пока первая операция держит блокировку, вторая ждёт. После COMMIT вторая проверяет актуальные данные и получает ошибку пересечения.

Все операции бронирования и ремонта одного номера используют одинаковое имя блокировки. Поэтому ремонт и бронь тоже не могут одновременно занять одни даты.

Это простое решение с компромиссом: даже операции на разные даты одного номера выполняются последовательно. Для небольшого проекта такая предсказуемость удобна; для большой системы понадобился бы анализ нагрузки.

## Что делает транзакция

Транзакция объединяет изменения в одну операцию. Успех — COMMIT. Ошибка — ROLLBACK. Создание бронирования и запись его начального статуса в историю должны завершиться вместе.

`SET XACT_ABORT ON` помогает корректно реагировать на ошибки выполнения. `TRY/CATCH` позволяет проверить состояние транзакции, откатить её и передать исходную ошибку вызывающему коду через THROW.

Процедуры вызываются без внешней транзакции: каждая сама управляет своей. Это выбранный контракт проекта, а не универсальное правило для всех баз данных.

## Зачем нужна идемпотентность платежей

Приложение отправило запись платежа, но не получило ответ из-за обрыва соединения. Если оно просто повторит INSERT, платёж может записаться дважды.

Здесь запрос содержит уникальный `Reference`. При повторе тех же параметров процедура возвращает прежний `PaymentID`. Если тот же Reference пришёл с другой суммой или другой бронью, процедура возвращает ошибку.

База только записывает платежи. Она не подключена к банку и не списывает реальные деньги.

## Как работает возврат

Бронь стоит 600 PLN. Гость внёс 200 PLN. Тогда:

- TotalAmount = 600.
- NetPaid = 200.
- BalanceDue = 400.

После отмены стоимость становится нулевой, но запись оплаты остаётся:

- TotalAmount = 0.
- NetPaid = 200.
- BalanceDue = −200 — нужно вернуть 200 PLN.

После REFUND на 200 PLN NetPaid и BalanceDue становятся равны нулю. История денег сохраняется.

## Почему нельзя просто соединить все таблицы через JOIN

Допустим, у брони две услуги и три платежа. JOIN брони с обеими таблицами даст шесть сочетаний. Если затем посчитать SUM, стоимость услуг и сумма платежей будут завышены.

В `vBookingFinancials` услуги сначала суммируются до одной строки на бронь. Платежи тоже суммируются отдельно до одной строки на бронь. Только после этого результаты соединяются с Booking.

Это важная тема для Data Engineering: перед соединением нужно понимать **grain**, то есть что означает одна строка каждого набора данных.

## Как объяснить отчёты

Booked occupancy — доля доступных номеро-ночей, занятых неотменёнными бронированиями.

ADR — сумма стоимости забронированных ночей, делённая на число этих ночей.

RevPAR — та же стоимость, делённая на все доступные номеро-ночи.

Это плановые показатели бронирований. Они не равны деньгам на банковском счёте: гость может оплатить проживание раньше, позже или получить возврат. Денежный отчёт строится по Payment.RecordedAt.

Если бронь начинается 30 января и заканчивается 2 февраля, январю принадлежат две ночи, а февралю одна. `CalendarDate` разворачивает период в отдельные ночи и позволяет правильно распределить стоимость по месяцам.

Для месячного ADR нужно делить общую месячную выручку на общее число ночей. Просто усреднять дневные ADR неправильно, если в разные дни разное число бронирований.

| Почему SQL Server? | Нужны транзакции, T-SQL процедуры, ограничения, блокировки и анализ планов; проект целенаправленно реализован на этой СУБД |

| Как проверяешь гонки? | Два независимых соединения запускают операции одновременно; тест проверяет итог, а не только отсутствие исключения |
| Что проверяешь кроме успешного сценария? | Пересечения, границы дат, переполнение вместимости, переплаты, возвраты, неправильные статусы и права доступа |
| Это DWH? | Нет. Это OLTP-база с аналитическими представлениями; отдельное хранилище можно построить следующим этапом |
| Что бы улучшил? | Групповые брони, цены по отдельным ночам, фактические заезды/выезды, безопасные повторы сервисных запросов, миграции и отдельная витрина данных |

## Чего не нужно обещать

В проекте нет production-нагрузочного тестирования, реальных банковских интеграций, налогового учёта, интерфейса пользователя и полноценной миграционной системы. Отчёты используют текущие статусы и текущий список активных номеров, а не исторические снимки инвентаря.

Чётко объяснить эти границы полезнее, чем называть учебный проект готовой промышленной системой.
